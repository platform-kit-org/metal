`pk-metal top` shows one small tile for each machine and, below the tiles, all the details of the selected machine.
The screen updates when the cluster changes.
Three keys do the same work as [](cli:approve), [](cli:hold) and [](cli:retry).

## Synopsis

<CliSynopsis cmd="top" />

The command takes no arguments. It needs a terminal. In a script, use [](cli:status).

## What it shows

<dl>
  <dt>Header</dt>
  <dd>The number of nodes that are Ready, each [](kind:TalosCluster), and each [](kind:TalosRollout) that did not succeed. The count `needs a person` is the number of machines, BMCs, claims, clusters and rollouts that need a person in [](cli:status). This command does not read [](kind:EtcdBackupPolicy) objects, so only [](cli:status) shows a backup that is too old.</dd>
  <dt>Tile</dt>
  <dd>One machine in four lines. The lines show its name and a mark for each step from the BMC to the node. They also show the phase of the [](kind:Host), its block, and the operation or the node.</dd>
  <dt>Detail panel</dt>
  <dd>The selected machine, as wide as the terminal: its BMC, the [](kind:Host), the claim, the operation and the [](kind:TalosNode). Long messages continue on the next lines. In a wide terminal, the machine and the cluster show in two columns.</dd>
  <dt>Operation line</dt>
  <dd>The step that runs, for example `5/9 setBootOverride`, or a mark that the operation waits for approval.</dd>
  <dt>With [`--fleet`](cli:top#--fleet)</dt>
  <dd>The state of the simulated BMC: power, media, boot override and the last Redfish call. Also the state of the virtual machine and the last console lines. The console fills the remaining height of the terminal.</dd>
  <dt>With [`--workload-kubeconfig`](cli:top#--workload-kubeconfig)</dt>
  <dd>The Ready condition of each node in the workload cluster. If the workload cluster does not answer yet, for example while its first control plane installs, the program does not stop. It tries again every 5 seconds.</dd>
</dl>

Without `--fleet`, the command works the same with real hardware.

## Keys

| Key | Effect |
| --- | --- |
| <kbd>Tab</kbd>, arrows | Select a machine. |
| <kbd>a</kbd> | Show the plan of the operation that waits for approval. Then <kbd>y</kbd> approves it. All other keys change nothing. |
| <kbd>h</kbd> | Hold the claim of the machine, or remove the hold. |
| <kbd>r</kbd> | Retry the failed or aborted operation of the machine. |
| <kbd>q</kbd>, <kbd>Escape</kbd> | Stop the program. |

The key <kbd>a</kbd> follows the rules of [](cli:approve).
If the plan is on the screen for more than five minutes, <kbd>y</kbd> approves nothing. Push <kbd>a</kbd> again.
If the operation or its plan changed after the program showed it, the approval fails and nothing changes.

<Callout type="caution">
Read the plan before you push <kbd>y</kbd>. An approved install overwrites the disk that the plan names.
</Callout>

## Examples

Watch real hardware.

```sh
pk-metal top
```

Watch the virtual lab. The simulator serves the state of its machines on port 8440.

```sh
pk-metal --kubeconfig .lab/kubeconfig top --fleet http://127.0.0.1:8440/state
```

In the lab, [](lab:up) prints this command with the correct paths.
