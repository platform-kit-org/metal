In the virtual lab, the machines are simulated BMCs and virtual machines. In this tutorial you use one real server.
At the end, the server runs Talos as a cluster with one control plane.

## What you make

- A management cluster in kind on your workstation, with the operator.
- One [](kind:Host) for your server, found through its BMC.
- One Talos cluster, `first`, with one node, `cp-1`, that is `Ready`.

<Callout type="warning">
The install overwrites the disk that you select. Use a server with no data that you must keep.
The repository has no record of an install on real hardware. Read [](ref:status) and [](ref:hardware) before you start, and stay near the server.
</Callout>

## Time and prerequisites

<dl>
  <dt>Time</dt>
  <dd>About one hour. The install takes about ten minutes.</dd>
  <dt>Hardware</dt>
  <dd>One x86-64 server in UEFI boot mode, with Secure Boot off. Its Redfish BMC has the license for virtual media. One free static address for the node. See [](ref:hardware).</dd>
  <dt>Network</dt>
  <dd>Your workstation reaches the BMC on TCP 443. The BMC reaches your workstation on TCP 30443. The node reaches the internet.</dd>
  <dt>BMC network</dt>
  <dd>The BMC downloads the installer and the config from the media service of the operator. The operator downloads the installer from `factory.talos.dev`. See [The BMC and the image factory](howto:network-checklist#the-bmc-and-the-image-factory).</dd>
  <dt>Tools</dt>
  <dd>A Linux workstation with Docker Engine and a clone of the repository. `mise install` gives you kind, kubectl and talosctl. `eval "$(mise activate bash)"` puts them on the `PATH`. Stage 1 builds `pk-metal`.</dd>
  <dt>Knowledge</dt>
  <dd>Read [](tut:lab-first-cluster) first. This tutorial uses the same steps.</dd>
</dl>

## Steps

### 1. Check the BMC

<Steps>

1. Build the tool, and put it on your `PATH`.

   ```sh
   mise run build && export PATH=$PWD/metal/bin:$PATH
   ```

2. Put the BMC password in the environment.

   ```sh
   read -rs PK_METAL_BMC_PASSWORD && export PK_METAL_BMC_PASSWORD
   ```

3. Check the BMC.

   ```sh
   pk-metal check --insecure https://192.0.2.21
   ```

4. Count the `media:` lines that do not show `dialect=none`. One such line means a BMC with one slot.

5. Read the inventory into a file.

   ```sh
   pk-metal inventory --insecure --node cp-1 https://192.0.2.21 > cp-1-inventory.yaml
   ```

6. Write down these values: the serial number, the BMC MAC, the node NIC MAC and the install disk serial.
   A disk behind a RAID volume has no serial in the inventory. See the install disk in [](ref:hardware).

</Steps>

**Checkpoint.** The last line of the check is `check:    OK (read-only)`. See [](howto:check-a-bmc) to read the other lines.

### 2. Start the operator

This stage is a short form of [](howto:install-operator). That page explains each file.

<Steps>

1. Copy `lab/kind.yaml` to `kind.yaml`. Set `name` to `bootstrap`, so that the lab tasks do not use the cluster. Set `listenAddress` to the address of your workstation on the BMC network.

2. Make the kind cluster.

   ```sh
   kind create cluster --config kind.yaml
   ```

3. Build the operator image. The last line of the output is the image reference, for example `pk-metal:4f0c2d1a9b3e`.

   ```sh
   mise run image
   ```

4. Load the image into kind. Use your image reference.

   ```sh
   kind load docker-image pk-metal:4f0c2d1a9b3e --name bootstrap
   ```

5. Copy the sample overlay.

   ```sh
   mkdir -p overlays && cp -r metal/config/samples/site-overlay overlays/site
   ```

6. In `overlays/site/kustomization.yaml`, replace `../../` with `../../metal/config/` in the three paths: the base and the two components. Set `images` to `newName: pk-metal` and `newTag` to your tag.

7. In `overlays/site/manager_args.yaml`, set `--media-url=https://<workstation address>:30443`.

8. In `overlays/site/ledger.yaml`, write one line: the BMC MAC and `https://192.0.2.21`.

9. In `overlays/site/networkpolicy.yaml`, set the CIDR of your BMC network. Until you set it, each mount fails with a connection error. See [](ref:media-store#network-policy).

10. In `overlays/site/kustomization.yaml`, remove the comment marks from the patch of `pk-metal-media`. kind replaces the BMC address with a node address (SNAT), and the patch prevents this.

11. Decide how the manager checks the BMC certificate. See [BMC certificates](howto:install-operator#bmc-certificates). For this first test on a closed BMC network, you can remove `--bmc-ca-secret=bmc-ca`. The manager then pins the key that the BMC shows at the first contact.

12. If the BMC has one slot, remove the comment mark from the component `media-store` in `overlays/site/kustomization.yaml`.

13. Apply the overlay.

    ```sh
    kubectl apply --server-side -k overlays/site
    ```

</Steps>

**Checkpoint.** `kubectl -n pk-metal get pods` shows the manager as `Running`.

### 3. Enroll the server

<Steps>

1. Make the credentials Secret.

   ```sh
   kubectl -n pk-metal create secret generic bmc-factory \
     --from-literal=username=admin --from-literal=password="$PK_METAL_BMC_PASSWORD"
   ```

2. Write the [](kind:Asset). Use your values for the marked lines.

   ```yaml title="asset.yaml"
   apiVersion: metal.platform-kit.org/v1alpha1
   kind: Asset
   metadata:
     name: first-server
   spec:
     cid: "FIRST-01"              # your asset tag
     serial: "ABC1234567"         # stage 1: the serial number
     bmcMac: "0c:c4:7a:12:34:56"  # stage 1: the BMC MAC, lower case
     credentialsRef:
       name: bmc-factory          # the Secret of step 1
   ```

3. Apply the Asset.

   ```sh
   kubectl apply -f asset.yaml
   ```

4. Monitor the Host.

   ```sh
   kubectl get hosts -w
   ```

</Steps>

**Checkpoint.** One Host is `Available`. If it shows `Mismatch`, see [](rb:host-mismatch).
If no Host comes and `kubectl get managementendpoints` shows `Unreachable`, the cause is usually the BMC certificate. See [](rb:bmc-unreachable).

### 4. Define the cluster

<Steps>

1. Make the secrets bundle and put it into a Secret.

   ```sh
   talosctl gen secrets -o secrets.yaml
   ```

2. Make the Secret from the file.

   ```sh
   kubectl -n pk-metal create secret generic first-talos-secrets --from-file=secrets.yaml
   ```

3. Write the [](kind:TalosCluster) `first` and the [](kind:TalosNode) `cp-1` into one file. Use your values for the marked lines.

   ```yaml title="first.yaml"
   apiVersion: os.platform-kit.org/v1alpha1
   kind: TalosCluster
   metadata:
     name: first
   spec:
     talosVersion: v1.14.6
     kubernetesVersion: v1.36.2
     endpoint: https://192.0.2.31:6443  # the node address, with the port
     controlPlane:
       allowScheduling: true            # pods can run on the one node
     secretsRef:
       namespace: pk-metal
       name: first-talos-secrets        # the Secret of step 2
   ---
   apiVersion: os.platform-kit.org/v1alpha1
   kind: TalosNode
   metadata:
     name: cp-1
   spec:
     clusterRef:
       name: first
     role: controlplane
     installDiskSelector:
       serial: "S4EVNX0R123456"         # stage 1: the install disk serial
     network:
       links:
         - name: lan
           hardwareAddr: "0c:c4:7a:ab:cd:ef"  # stage 1: the node NIC MAC, lower case
           addresses:
             - 192.0.2.31/24                  # the free static address
           routes:
             - gateway: 192.0.2.1             # the gateway of that network
   ```

4. Apply the file.

   ```sh
   kubectl apply -f first.yaml
   ```

5. Wait until the operator rendered the config.

   ```sh
   kubectl wait --for=condition=Rendered talosnode/cp-1 --timeout=120s
   ```

</Steps>

**Checkpoint.** The command prints `talosnode.os.platform-kit.org/cp-1 condition met`. See [](howto:define-a-cluster) for the fields.

### 5. Claim and install

<Provision />

<Steps>

1. Write a [](kind:HostClaim) `cp-1`. It gives the machine of the Asset to the TalosNode.

   ```yaml title="claim.yaml"
   apiVersion: metal.platform-kit.org/v1alpha1
   kind: HostClaim
   metadata:
     name: cp-1
     namespace: default
   spec:
     assetRef:
       name: first-server
     os:
       nodeRef:
         name: cp-1
   ```

2. Apply it as a member of the admin group. Only that group can apply a claim that installs a node, and the kind admin is not a member.

   ```sh
   kubectl apply --as="$USER" --as-group=pk-metal:admins --as-group=system:authenticated -f claim.yaml
   ```

   This command uses impersonation. It is a shortcut for a test cluster of your own.
   On a production cluster, your login gives you the group. See [The admin group and the approvers](howto:install-operator#the-admin-group-and-the-approvers).

3. List the operations that wait. Without a name, the command approves nothing.

   ```sh
   pk-metal approve
   ```

4. Read the plan of the install and approve it. Use the name from the list. Type `y` when the command asks.

   ```sh
   pk-metal approve pk-metal/<name>
   ```

   The operator proposed the install, so you can approve it.

5. Monitor the Host and the remote console of the BMC.

   ```sh
   kubectl get hosts -w
   ```

</Steps>

**Checkpoint.** The Host is `Provisioned`. `kubectl get taloscluster first` shows `AVAILABLE` `True`.

### 6. Use the cluster

<Steps>

1. Write the kubeconfig to a file.

   ```sh
   kubectl -n pk-metal get secret first-kubeconfig -o jsonpath='{.data.kubeconfig}' | base64 -d > first.kubeconfig
   ```

2. Show the node.

   ```sh
   kubectl --kubeconfig first.kubeconfig get nodes
   ```

</Steps>

**Checkpoint.** `cp-1` is `Ready`.

## If a stage does not give its checkpoint

| What you see | Go to |
| --- | --- |
| The manager pod is not `Running` | [If it fails](howto:install-operator#if-it-fails) of the install how-to |
| The endpoint is `Unreachable` | [](rb:bmc-unreachable) |
| The operation fails at `insertMedia` | If the BMC log shows a connection error: steps 9 and 10 of stage 2. Else [](rb:media-slot-busy), and [The BMC and the image factory](howto:network-checklist#the-bmc-and-the-image-factory) |
| The Host stays `Provisioning`, and the console shows no boot | [](rb:node-not-ready), and the boot mode and Secure Boot in [](ref:hardware) |
| The operation is `Failed` | [](rb:operation-failed) |

## What you learned

- The operator finds a machine through its BMC and the ledger: [](concept:ledger), [](concept:identity).
- It boots from virtual media, not PXE: [](concept:virtual-media-boot).
- It changes a machine only after your approval: [](concept:approval).
