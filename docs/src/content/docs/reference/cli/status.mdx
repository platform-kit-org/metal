`pk-metal status` shows the state of all machines in one view. It reads only.
Below each table, it gives the reason for each row that has a block or a failure, and the command to run next.
For a running operation, it gives the step and what the step waits for.

## Synopsis

<CliSynopsis cmd="status" />

The command takes no arguments.

## Flags

<CliFlags cmd="status" />

## What it does

1. The command lists the objects of the operator in the management cluster.
2. It makes one row for each object and finds the rows that need a person.
3. It prints the tables, or one JSON object with `-o json`.
4. It exits with code 2 if one row or more needs a person.

### Tables

| Table | Rows | Columns |
| --- | --- | --- |
| `HOST` | Each [](kind:Host) | Asset, vendor, phase, claim, node and address, BMC paths that answer, block |
| `OPERATION` | Each [](kind:HostOperation) that did not succeed | Host, phase, approver, block |
| `ENDPOINT` | Each [](kind:ManagementEndpoint) | Asset, vendor, phase, address, block |
| `CLAIM` | Each [](kind:HostClaim) that has no machine | Asset, phase, block. A hold shows as `(on hold)`. |
| `CLUSTER` | Each [](kind:TalosCluster) | Talos and Kubernetes versions (spec and nodes), ready nodes, etcd, backup, API |
| `NODE` | Each [](kind:TalosNode) | Cluster, role, host, address, version, boot stage, readiness |
| `ROLLOUT` | Each [](kind:TalosRollout) that did not succeed | Cluster, kind, nodes done of the plan, state, approver |

The command shows `OPERATION`, `CLAIM`, `CLUSTER`, `NODE` and `ROLLOUT` only when they have rows.
A failed operation stays in the table until you run [](cli:retry).
The note of a failed step of a rollout names the rollout and not `pk-metal retry`. The rollout does not make the step again.

### Rows that need a person

<dl>
  <dt>Host</dt>
  <dd>The Host or its claim has a block, or the phase is Failed.</dd>
  <dt>Operation</dt>
  <dd>The operation waits for approval, the phase is Failed or Aborted, or the operation has a block. An operation waits for approval when it needs one, nobody approved it, and it did not end. [](cli:approve) uses the same rule.</dd>
  <dt>Endpoint</dt>
  <dd>The endpoint has a block, or the phase is Unreachable or Mismatch.</dd>
  <dt>Claim</dt>
  <dd>The claim has a block, or the phase is Ambiguous.</dd>
  <dt>Cluster</dt>
  <dd>The cluster is bootstrapped and its etcd or its Kubernetes API is not healthy. Or the backup is not current.</dd>
  <dt>Node</dt>
  <dd>The cluster is bootstrapped, the node reported a version, and the node is not Ready.</dd>
  <dt>Rollout</dt>
  <dd>The rollout waits for approval, cannot make a plan, has a changed plan, stopped after the first node, failed, or a person aborted it.</dd>
</dl>

Two blocks of an operation need no person: `OperationQueued` and `OutsideMaintenanceWindow`. The operator continues by itself.

Use the JSON output in a script. The exit status tells the script if a person must act.

```sh
pk-metal status -o json | jq '.hosts[] | select(.needsAttention)'
```

Show the status again each 10 seconds.

```sh
watch -n 10 pk-metal status
```

## JSON output

`-o json` prints the same facts as one object.

| Key | Content |
| --- | --- |
| `version` | `1`. Keys do not change while the version is 1. New keys can come. |
| `needsAttention` | `true` if one row or more needs a person. |
| `hosts` | `name`, `asset`, `vendor`, `phase`, `claim`, `node` (`name`, `address`, or `null`), `pathsUp`, `pathsTotal`, `blockedOn`, `message`, `needsAttention` |
| `operations` | `namespace`, `name`, `host`, `phase`, `approvedBy`, `awaitsApproval`, `blockedOn`, `message`, `needsAttention`, `rollout` (the [](kind:TalosRollout) of a step) |
| `endpoints` | `name`, `asset`, `vendor`, `phase`, `address`, `blockedOn`, `message`, `needsAttention` |
| `claims` | `namespace`, `name`, `asset`, `host`, `phase`, `blockedOn`, `message`, `onHold`, `needsAttention` |
| `clusters` | `name`, `talosVersion`, `talosVersionsRunning`, `kubernetesVersion`, `kubernetesVersionRunning`, `controlPlanes`, `readyControlPlanes`, `workers`, `readyWorkers`, `available`, `etcd`, `bootstrappedAt`, `backup`, `backupMessage`, `message`, `needsAttention` |
| `nodes` | `name`, `cluster`, `role`, `host`, `address`, `version`, `stage`, `ready`, `message`, `needsAttention` |
| `rollouts` | `name`, `cluster`, `kind`, `nodesDone`, `nodesTotal`, `state`, `approvedBy`, `message`, `needsAttention` |

Each key is always there. An empty value is `""`.
The lists `operations`, `claims` and `rollouts` hold all objects, also the operations and rollouts that succeeded and the claims that are bound.

## Objects

| Object | Access | Purpose |
| --- | --- | --- |
| [](kind:Host), [](kind:ManagementEndpoint), [](kind:HostClaim), [](kind:HostOperation) | list | The first four tables. |
| [](kind:TalosCluster), [](kind:TalosNode), [](kind:TalosRollout), [](kind:EtcdBackupPolicy) | list | The cluster, node and rollout tables, and the `BACKUP` column. A cluster without these kinds shows no such tables. |

The command fails if it cannot read one of these kinds. It writes nothing.
