## Goal

Run the operator on the Talos cluster that it installed, and stop the bootstrap cluster on your workstation.

## Before you start

- The bootstrap cluster (usually kind) is the current kubeconfig context.
- You have the kubeconfig of the target cluster, for example `mgmt.kubeconfig`.
- No operation runs. No rollout is under way. No claim is in deletion. [](cli:status) shows this.
- The target has storage for the [](term:media-store), or you accept `--media-store=ephemeral`.
- The target can reach each BMC, and each BMC can reach the target. See [](howto:network-checklist).
- The operator image is in a registry that the nodes of the target can pull from. An image that you loaded into kind is not. See [](howto:install-operator).
- The target has a node that accepts ordinary pods: a worker, or control planes with `controlPlane.allowScheduling: true`.

## Steps

<Steps>

1. Make sure that nothing runs.

   ```sh
   pk-metal status
   ```

   No operation is in the phase `Running`.

2. Start the move. Give the media address on a node of the target, and the image in your registry.

   ```sh
   pk-metal pivot --to mgmt.kubeconfig --media-url https://192.0.2.11:30443 \
     --image registry.example.org/platform/pk-metal:4f0c2d1a9b3e
   ```

   Without `--image`, the target uses the image reference of the source.

3. Read the list of network paths that the command shows. Check it with your network team.

4. Type `y` to start.

   The last lines say that the new manager runs and settled.

5. Make the target your current context, and examine the fleet.

   ```sh
   pk-metal --kubeconfig mgmt.kubeconfig status
   ```

6. When you do not need the bootstrap cluster, delete it. Use the name of your kind cluster.

   ```sh
   kind delete cluster --name bootstrap
   ```

</Steps>

<Callout type="caution">
Do not delete only the pk-metal objects in the bootstrap cluster.
Their finalizers wait for an operator that does not run there, and the deletion does not end. Delete the full cluster.
</Callout>

## Verify

- `pk-metal status` on the target shows each Host in the same phase as before.
- Each handed-off claim shows `HandedOff`.
- No new [](kind:HostOperation) exists.

## Roll back

Run the operator in the bootstrap cluster again. You need the kubeconfigs of both clusters, for example `bootstrap.kubeconfig` and `mgmt.kubeconfig`. The pivot output says if the new manager runs.

| The new manager | Method |
| --- | --- |
| Does not run | Stop it, then scale the old manager up again. |
| Runs | Pivot in the other direction. |

<Callout type="warning">
Do not run the two managers at the same time. Two operators then act on the same machines.
</Callout>

### The new manager does not run

<Steps>

1. Stop the new manager. If the move stopped before it started the new manager, this step changes nothing.

   ```sh
   kubectl --kubeconfig mgmt.kubeconfig -n pk-metal scale deployment pk-metal-manager --replicas=0
   ```

2. Make sure that the list shows no manager pod.

   ```sh
   kubectl --kubeconfig mgmt.kubeconfig -n pk-metal get pods
   ```

3. Give the source its manager back.

   ```sh
   kubectl --kubeconfig bootstrap.kubeconfig -n pk-metal scale deployment pk-metal-manager --replicas=1
   ```

4. Make sure that the manager runs.

   ```sh
   pk-metal --kubeconfig bootstrap.kubeconfig status
   ```

</Steps>

The objects on the target are a copy that nothing acts on. Remove them, or keep them for the next move.

### The new manager runs

<Steps>

1. Move from the new cluster to the bootstrap cluster.

   ```sh
   pk-metal --kubeconfig mgmt.kubeconfig pivot --to bootstrap.kubeconfig
   ```

   The source of the first move accepts the move back. The move removes objects that are gone on the new source.

2. Type `y` to start.

</Steps>

After the roll back, `pk-metal --kubeconfig bootstrap.kubeconfig status` shows each Host in its phase. The manager on the other cluster has zero replicas.

## If it fails

| What you see | Fix |
| --- | --- |
| The move refuses to start | The message says what to do. Do it, then run the same command again. |
| The move stops in the middle | Run the same command again. It continues from where it stopped. |
| The target has no storage | Give it a default StorageClass, or use `--media-store=ephemeral`. |
| The manager pod on the target shows `ImagePullBackOff` | The nodes cannot pull the image. Push it to a registry, then run the command again with `--image`. |
| The manager pod on the target stays `Pending` | No node accepts the pod. Add a worker, or set `controlPlane.allowScheduling: true` and let the rollout complete. Then run the command again. |
| The new operator proposed an operation | The move fails and names it. See [Roll back](#roll-back). |
