## Goal

See what runs, what waits and what is wrong, from a quick look to a page.

## Three ways to look

| Tool | For | Reads |
| --- | --- | --- |
| [](cli:status) | A quick look, a cron check | The management cluster |
| [](cli:top) | A live view, one tile for each machine | The management cluster |
| Prometheus metrics and alerts | Dashboards and pages | The `/metrics` endpoint of the manager |

## Use pk-metal status in a check

<Steps>

1. Run the command and read its exit status.

   ```sh
   pk-metal status; echo "exit=$?"
   ```

2. Read the result.

   | Exit | Meaning |
   | --- | --- |
   | `0` | Nothing needs a person. |
   | `1` | The command could not read the cluster. |
   | `2` | Something needs a person: an approval, a failure, an unhealthy etcd, a stale backup, a node that is not `Ready`. A rollout that waits for approval or a resume also counts. |

3. For a script, use the JSON form.

   ```sh
   pk-metal status -o json
   ```

</Steps>

## Start the alerts

<Steps>

1. Make sure that the cluster has the Prometheus Operator. The files use its kinds `PrometheusRule` and `ServiceMonitor`.

2. Open `metal/config/prometheus/metrics_reader.yaml`. Set the subject of the `ClusterRoleBinding` to the service account of your Prometheus.

   The manager serves `/metrics` over HTTPS. It answers only a caller whose token may `get` the URL `/metrics`.

3. If your Prometheus selects ServiceMonitors by a label, add that label to `metal/config/prometheus/servicemonitor.yaml`.

4. Apply the rules, the ServiceMonitor and the role.

   ```sh
   kubectl apply -k metal/config/prometheus
   ```

5. Make sure that Prometheus scrapes the manager. In Prometheus, this query gives `1`.

   ```text
   up{job="pk-metal-metrics", namespace="pk-metal"}
   ```

</Steps>

Each alert has a `runbook_url` annotation. [Alerts](rb:index#alerts) gives each alert, when it fires, and its runbook.

<Callout type="caution">
`PkMetalMetricsAbsent` cannot page when Prometheus stops together with the management cluster.
Send this alert to a receiver outside the management cluster, or watch the manager from a second Prometheus.
</Callout>

To limit who can connect to the manager pod, edit and apply `metal/config/manager/networkpolicy.yaml`. It is not part of the base install. Only you know the BMC and Prometheus addresses of your site.

To check the rules with `promtool`, run `mise run metrics:rules`.

## Important metrics

All names start with `pk_metal_`.

<dl>
  <dt>`host_phase`, `host_blocked`</dt>
  <dd>The phase of each Host, and the reason when it waits.</dd>
  <dt>`operation_failed`, `operation_awaiting_approval_seconds`, `operation_blocked`</dt>
  <dd>Operations that need a person, and approved operations that did not start.</dd>
  <dt>`operation_running_seconds`</dt>
  <dd>How long a running operation is in its current step, with the step.</dd>
  <dt>`bmc_reachable`</dt>
  <dd>1 when the BMC answers Redfish.</dd>
  <dt>`talosnode_ready`, `taloscluster_available`</dt>
  <dd>Node and cluster health.</dd>
  <dt>`talosnode_expected_ready`, `taloscluster_expected_available`</dt>
  <dd>1 when the node or cluster must be healthy: the same rule as [](cli:status). The alerts use them, so an install does not page.</dd>
  <dt>`etcd_backup_last_success_timestamp_seconds`, `etcd_backup_interval_seconds`</dt>
  <dd>The time of the newest verified snapshot, and the shortest interval of the backup policies of the cluster.</dd>
  <dt>`rollout_condition`</dt>
  <dd>1 for each rollout that did not succeed, with the reason where it stands. A later rollout of the cluster can replace a `PlanChanged` rollout. Then it has no series.</dd>
  <dt>`rollout_nodes_done`, `rollout_nodes_total`</dt>
  <dd>The progress of each rollout.</dd>
  <dt>`admission_gate_degraded`</dt>
  <dd>1 for each admission policy of the approval gate that is missing or does not deny. See [](ref:admission-policies).</dd>
</dl>
