## pk-metal status

One table for each kind of thing: HOST, OPERATION, ENDPOINT, CLAIM, CLUSTER, NODE, ROLLOUT.
Under each table, one line for each row that needs a person, with the reason.

The command exits with `2` when something needs a person. [Exit status](cli:status#exit-status) gives each code.
An operation that waits for its window or for another operation on the same Host does not count. That is the plan at work.
A rollout that runs a node or waits for health between nodes does not count either. An alert pages when that wait is too long.

## Metrics

All series start with `pk_metal_`. [Metrics](ctrl:manager#metrics) lists them.
The series `talosnode_expected_ready` and `taloscluster_expected_available` use the same rule as pk-metal status: a node of a bootstrapped cluster that answered before.

## Alerts

The directory `metal/config/prometheus` holds a PrometheusRule, a ServiceMonitor and the role that lets Prometheus read the metrics. Apply it where the Prometheus Operator runs. Each alert links to its runbook. [](howto:monitor) lists the alerts.

The alerts follow the same rules as pk-metal status. An install does not page. A rollout that waits for health between nodes does not page.
One alert, `PkMetalMetricsAbsent`, fires when the metrics are gone. Without it, a stopped manager would look healthy: each other alert resolves.
