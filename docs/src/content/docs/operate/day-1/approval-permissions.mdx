## Goal

Give each person the rights for their work. Choose if a person can approve a change that they proposed.

## Before you start

- You have the site overlay from [](howto:install-operator).
- You know the groups of your identity provider, or the `O=` fields of your client certificates.

## The roles

| Role | What it does | How a person gets it |
| --- | --- | --- |
| Operator | Proposes most operations and rollouts. It never approves. | The service account `pk-metal/pk-metal-manager`. The base binds it. |
| Proposer | Proposes an operation or a rollout: [](cli:reboot), `pk-metal restore plan --propose`, or a [](kind:TalosRollout) of kind `Reboot`. | `create` on `hostoperations` or `talosrollouts`. `pk-metal-admin` has it. For proposers outside the admin group, write a ClusterRole. |
| Approver | Approves with [](cli:approve) and [](cli:rollout). Also aborts, pauses, resumes, and lifts guards. | The ClusterRole `pk-metal-approver`. `bindings.yaml` binds it to a group. |
| Admin group | Makes the decisions that no approval covers. See [Who may do what](ref:rbac#who-may-do-what). | The group in the ConfigMap key `adminGroup`, default `pk-metal:admins`. The membership comes from the login, not from a binding. |
| On call | Follows the [runbooks](rb:index): reads each kind, deletes failed operations, holds claims. It cannot approve. | The ClusterRole and the Role `pk-metal-oncall`. `bindings.yaml` binds both to a group. |
| GitOps service account | Applies the kinds that you keep in git. | Its own binding. Never give it `pk-metal-approver`. See [](concept:gitops). |

A person can have more than one role. A person on call usually also has `pk-metal-approver`.

## Choose the `selfApproval` setting

The key `selfApproval` in the ConfigMap `hostoperation-approval` tells if a person can approve their own change. It applies to operations and to rollouts. A change is "their own" when one of these names the person:

- `spec.proposedBy`: the person proposed it.
- `spec.requestedBy`: the edit of the person made the operator propose it. See [Who asked for a change](#who-asked-for-a-change).

| Value | What it prevents | What it does not prevent |
| --- | --- | --- |
| `Allowed` (the default) | The operator approves nothing. A person approves in their own name only, and only one time. Nobody creates an approved object. | One person with the proposer and the approver role changes a machine alone. The record names that person as requester and as approver. |
| `Forbidden` | The same, and also: one account alone cannot change a machine. A second person reads each plan before it runs. | The operator and the admin group can still create operations that need no approval. A GitOps service account is the requester of what it applies, not the person who wrote the commit. See [](ref:threat-model). |

- Select `Forbidden` if two or more approvers can answer in time.
- Select `Allowed` for a small team. Then examine the approvals that a person gave to their own proposals:

  ```sh
  kubectl get hostoperations,talosrollouts -A -o json | jq -r '.items[]
    | select(.spec.approval.approvedBy as $a | $a != null
        and (.spec.proposedBy == $a or ((.spec.requestedBy // []) | index($a))))
    | "\(.kind) \(.metadata.name) \(.spec.approval.approvedBy)"'
  ```

- The API server reads each other value as `Forbidden`, and its message names the value.

## Steps

[](howto:install-operator) puts your groups into `bindings.yaml` and the first value of `selfApproval` into `approval.yaml`. These steps change the value after the install.

After the first apply, only a member of the admin group can change or delete the ConfigMap. The `settings-guard` policy refuses each other person, also the cluster admin who applies the overlay. The operator writes a `settings.changed` line in the [](ref:audit-trail) for each change.

<Steps>

1. Ask a member of the admin group to set the value.

   ```sh
   kubectl -n pk-metal patch configmap hostoperation-approval --type merge \
     -p '{"data":{"selfApproval":"Forbidden"}}'
   ```

2. Put the same value in `approval.yaml`. Then the next apply of the overlay does not change the ConfigMap, and `settings-guard` does not refuse it.

3. Read the setting back.

   ```sh
   kubectl -n pk-metal get configmap hostoperation-approval -o jsonpath='{.data.selfApproval}{"\n"}'
   ```

   The API server uses the new value after a few seconds.

4. Ask each approver to examine their rights.

   ```sh
   kubectl auth can-i patch hostoperations -n pk-metal
   ```

   The output is `yes`.

5. Ask each person on call to examine their rights. The runbooks read the manager log.

   ```sh
   kubectl auth can-i get pods --subresource=log -n pk-metal
   ```

   The output is `yes`.

</Steps>

## Who asked for a change

The operator proposes most changes itself, as the result of an edit. For example, a new `talosVersion` on a [](kind:TalosCluster) becomes a rollout, and a `metal.platform-kit.org/wipe` mark on a Host becomes a wipe operation. The proposal names the operator as its proposer. So the person who made the edit must also be on the record. Each such edit names its user in the annotation `metal.platform-kit.org/requested-by`. The policy [`requested-by`](ref:admission-policies#requested-by) has the rules, and [`requested-by-stamp`](ref:admission-policies#requested-by-stamp) writes the annotation for you on Kubernetes 1.36 or later.

- On an older release, set the annotation in the same request. The pk-metal commands do this for you, for example [](cli:upgrade), [](cli:wipe), and `pk-metal rollout pause`.
- A delete of such an object needs the annotation before the delete. The API server cannot stamp a delete. The pk-metal commands set it first, for example [](cli:scale) and [](cli:replace). With `kubectl`, set it first:

  ```sh
  me=$(kubectl auth whoami -o jsonpath='{.status.userInfo.username}')
  kubectl annotate talosnode node-2 --overwrite "metal.platform-kit.org/requested-by=$me"
  kubectl delete talosnode node-2
  ```

- To make a change of another person your own, set your own username.
- The operator copies the names from the objects behind a proposal into `spec.requestedBy` of the operation or rollout.
- An install applies the config of the node. So the install also names the last editor of the [](kind:TalosCluster). It also names the last editor of each patch ConfigMap of the node. A rollout names the same persons.
- A BIOS or firmware change names the last editor of each profile that it applies. A profile can select the Host by a label of the [](kind:HostClaim). Then the change also names the last editor of the claim. A label that a person puts on the Host directly names nobody.
- A rollout that the operator proposed ends with `PlanChanged` if a person who is not in its `spec.requestedBy` changes what it applies. The operator then proposes it again, with the new names.
- A GitOps controller is the requester of what it applies, not the person who wrote the commit. See [The requester in git](concept:gitops#the-requester-in-git).

## Guard-lift annotations

Two annotations on a [](kind:HostOperation) lift the cluster guard or a maintenance window for that operation. Each person with `patch` on operations can set them, before or after the approval. That is each holder of `pk-metal-approver`. `selfApproval` does not apply to annotations. See [Named guard lifts](ref:audit-trail#named-guard-lifts).

<Callout type="caution">
Give `pk-metal-approver` only to persons who may decide to lift these rules. An annotation that a person adds after the approval does not go through the approval again. The [](ref:audit-trail) records each lift that the operator uses.
</Callout>

## Choose the retention

The key `retention` in the same ConfigMap tells how long the operator keeps a finished operation or rollout. The default is `30d`. Set `Forever` to keep each record until a person deletes it. See [Retention](ref:audit-trail#retention).
