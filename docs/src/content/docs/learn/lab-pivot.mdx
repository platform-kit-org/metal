At a real site, the operator starts in a small bootstrap cluster and installs the first Talos cluster.
Then it moves to that cluster. In this tutorial, you do this move in the lab.

## Steps

### 1. Start a lab with two clusters

1. If a lab runs, stop it and delete the disks.

   ```sh
   mise run lab:down && mise run lab:reset
   ```

2. Start the lab. [`PK_LAB_WORKLOAD`](lab:page/lab-yaml#pk_lab_workload) adds the second cluster to the spec.

   ```sh
   PK_LAB_NODES=1cp+0w PK_LAB_WORKLOAD=1cp+0w mise run lab:up
   ```

3. Install the first cluster.

   ```sh
   mise run lab:wait
   ```

<Checkpoint>
`lab:wait` ends with `converged after`. `mise run lab:status` shows two Hosts.
`pklab0001` is `Provisioned`. `pklab0002` is `Available`, because the claims of the second cluster are not applied.
</Checkpoint>

### 2. Move the operator

<Callout type="caution">
Do not start a second operator for the same machines.
During the move, [](cli:pivot) stops the operator in kind before it starts the operator on the Talos cluster.
</Callout>

1. Run the pivot round.

   ```sh
   mise run lab:pivot
   ```

2. Follow the output. Each line that starts with `==` is one part.

<TermReplay src="casts/lab-pivot.json" caption="A replay with example data." />

| Part in the output | What happens |
| --- | --- |
| `image registry on 10.77.0.1:5000` | The task starts an image registry on the workstation. |
| `operator image to 10.77.0.1:5000` | The task pushes the operator image to the registry. The first cluster pulls it from there. |
| `pk-metal pivot to TalosCluster lab` | The operator stops in kind. Its objects move. The operator starts on the cluster `lab`. |
| `deleting the kind cluster pk-metal` | The task deletes the kind cluster. `.lab/kubeconfig` now names the cluster `lab`. |
| `TalosCluster work, installed by the operator on lab` | The task applies `.lab/generated/workload/`, approves the install, and waits. |

The move fails if the new operator proposes an operation while pk-metal watches it (`--settle`, 90 seconds). See [](cli:pivot).

<Checkpoint>
The output has `settled: no new operation in 1m30s`. It ends with `The operator runs on TalosCluster lab and installed work from there.`
</Checkpoint>

### 3. Examine the result

1. Make sure that kind is gone.

   ```sh
   kind get clusters
   ```

   The cluster `pk-metal` is not in the list.

2. Show the operator on the first Talos cluster.

   ```sh
   kubectl --kubeconfig .lab/kubeconfig -n pk-metal get pods -o wide
   ```

3. Show the nodes of the second cluster.

   ```sh
   kubectl --kubeconfig .lab/second.kubeconfig get nodes
   ```

   ```console
   NAME     STATUS   ROLES           AGE   VERSION
   node-2   Ready    control-plane   3m    v1.36.2
   ```

4. Show the rack. The tasks now speak to the first Talos cluster.

   ```sh
   mise run lab:status
   ```

<Checkpoint>
Two Hosts are `Provisioned`. The operator pod runs on `node-1`. The second cluster has one `Ready` node.
</Checkpoint>

### 4. Stop the lab

1. Stop the lab and delete the disks.

   ```sh
   mise run lab:down && mise run lab:reset
   ```

   The disk of `node-1` holds the moved operator. `lab:reset` wipes it.

## What you learned

- The operator can manage the machine that it runs on: [](concept:self-protection).
- A pivot moves the objects and the operator, and it does not install a machine again: [](concept:pivot-model).
- In the lab, the moved operator keeps its media store in an `emptyDir`. A real site uses a volume. See [](cli:pivot).
