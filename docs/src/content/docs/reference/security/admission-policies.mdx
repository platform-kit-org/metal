RBAC says who may create or patch an object. It cannot see the name that a person writes into a field.
Nine [ValidatingAdmissionPolicies](term:vap) close that gap. They are [CEL](term:cel) in the API server: no webhook, no certificate, no pod.
Three MutatingAdmissionPolicies write your username into the annotations that these policies check. See [The name stamps](#the-name-stamps).

## At a glance

| Policy | Kind | Operations | Purpose |
| --- | --- | --- | --- |
| `hostoperation-approval` | [](kind:HostOperation), [](kind:TalosRollout) | CREATE, UPDATE | The approval gate of one operation or one rollout plan. |
| `hostclaim-provisioning` | [](kind:HostClaim) | CREATE, UPDATE | Who may choose the OS of a machine, and who may skip the boot approval. |
| `etcdbackuppolicy-guard` | [](kind:EtcdBackupPolicy) | CREATE, UPDATE | Who may choose who can read the etcd backups, and where they go. |
| `endpointprofile-guard` | [](kind:EndpointProfile) | CREATE, UPDATE | Who may change what the operator writes to the BMCs. |
| `taloscluster-credentials-guard` | [](kind:TalosCluster) | CREATE, UPDATE | Who may make the published admin credentials live longer than 24 hours. |
| `guard-lift` | HostOperation, HostClaim, [](kind:TalosNode), [](kind:Host) | CREATE, UPDATE | A guard lift or a decision names the person who sets it, and a reason. Only the operator removes `disk-not-wiped` without a named waiver. |
| `requested-by` | TalosCluster, TalosNode, HostClaim, [](kind:BiosProfile), [](kind:FirmwareProfile), Host, TalosRollout | CREATE, UPDATE, DELETE | If `selfApproval` is `Forbidden`, a change that makes the operator propose work names the user who asked for it. |
| `requested-by-patches` | ConfigMaps with `os.platform-kit.org/patch` | CREATE, UPDATE, DELETE | The rules of `requested-by` for the Talos config patches. |
| `settings-guard` | The ConfigMap `pk-metal/hostoperation-approval` | CREATE, UPDATE, DELETE | Only the admin group changes or deletes the site settings. |

All nine have these settings:

<dl>
  <dt>`failurePolicy: Fail`</dt>
  <dd>If the API server cannot evaluate the policy, it refuses the request.</dd>
  <dt>`validationActions: [Deny]`</dt>
  <dd>A failed rule refuses the request with reason `Forbidden`.</dd>
  <dt>Parameters</dt>
  <dd>All except `settings-guard`, which needs none: the ConfigMap `hostoperation-approval` in `pk-metal`. Key `operator` is the name of the manager. Key `adminGroup` is the admin group. Key `selfApproval` tells if a person can approve their own proposal.</dd>
  <dt>`parameterNotFoundAction: Deny`</dt>
  <dd>Without the ConfigMap, the API server refuses each request that a policy with parameters checks. The gate fails closed.</dd>
</dl>

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: hostoperation-approval
  namespace: pk-metal
data:
  operator: system:serviceaccount:pk-metal:pk-metal-manager
  adminGroup: pk-metal:admins
  selfApproval: Allowed
```

## The `selfApproval` setting

The approval policy reads the key `selfApproval`. It applies to operations and to rollouts.

| Value | A person approves their own proposal | Use it when |
| --- | --- | --- |
| `Allowed` | Yes. The record names the same person as proposer and approver. | The team is too small for review by two persons. |
| `Forbidden` | No. Another person must approve. | One account must not change a machine alone. |
| Key not set | Yes, as `Allowed`. | |
| Another value | No, as `Forbidden`. The message tells you to set a correct value. | |

The operator never approves, with each value. [](howto:approval-permissions) tells you how to choose.

## `hostoperation-approval`

The policy checks operations and rollouts. The CRD schema freezes the target, the actions, `approval.required` and `proposedBy`. The policy checks the rules that need the name of the requester.
The approval of a rollout also names the `planHash` that you read. The [](ctrl:talosrollout) runs the rollout only while that hash is the plan.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Nobody creates an operation or a rollout that is already approved. | CREATE | a HostOperation cannot be created pre-approved, or a TalosRollout … |
| 2 | `spec.proposedBy` is your own name. | CREATE | spec.proposedBy must name you |
| 3 | Only the operator or an admin creates an operation with `approval.required: false`. A rollout has no such field. | CREATE | only the operator or an admin may create an operation that needs no approval |
| 4 | An approval, once set, does not change. For a rollout, this includes the `planHash`. | UPDATE | approval is write-once |
| 5 | You approve as yourself: `approvedBy` is your name. | Approval write | you may only approve as yourself |
| 6 | The operator approves nothing. | Approval write | the operator approves nothing: a person with the pk-metal-approver role must approve |
| 7 | You approve your own proposal only if `selfApproval` is `Allowed` or not set. | Approval write | this site forbids approving your own proposal (selfApproval: Forbidden in ConfigMap pk-metal/hostoperation-approval): another person must approve |
| 8 | You approve a change that you asked for (`spec.requestedBy` names you) only if `selfApproval` is `Allowed` or not set. | Approval write | you asked for this change (spec.requestedBy names you: your edit made the operator propose it), and this site does not allow approving your own change |

<dl>
  <dt>Why rule 3</dt>
  <dd>Anybody else could skip the gate. The operator itself creates such operations in three cases. These are the node steps of an approved rollout, an install of a claim with `provisioning.approval: Automatic`, and a release that needs no person.</dd>
  <dt>Why rule 6 names the operator</dt>
  <dd>The operator proposes most operations. A person must approve them. RBAC also stops the operator: it has no `patch` on operations. See [](ref:rbac). Rule 6 is the second lock. No setting changes it.</dd>
  <dt>Why rule 7 is a setting</dt>
  <dd>A small team cannot always find a second person. With `Allowed`, the record still names who proposed and who approved. A value that is not `Allowed` or `Forbidden` closes the gate. The message names the value.</dd>
  <dt>Why rule 8</dt>
  <dd>The operator proposes most operations as the result of an edit by a person. Without rule 8, that person could approve the result of their own edit. The operator copies the names from the `requested-by` annotations into `spec.requestedBy`. The CRD schema freezes the field.</dd>
</dl>

Example: the manager proposed an operation. `jo` approves it.

```sh
kubectl -n pk-metal patch hostoperation install-node-07 --type merge \
  -p '{"spec":{"approval":{"approvedBy":"jo"}}}'
```

The policy accepts this only if the username of `jo` is `jo`. Use [](cli:approve). It writes your name.

## `hostclaim-provisioning`

A claim that names a [](kind:TalosNode) makes the operator mount the config of that node on the machine. A control-plane config carries the CA keys of the cluster. So these changes are an admin decision.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin sets or changes `spec.os.nodeRef`. | CREATE, UPDATE | only an admin may name the TalosNode a claim boots |
| 2 | Only an admin turns `spec.provisioning.approval` to `Automatic`. | CREATE, UPDATE | only an admin may waive provisioning approval |
| 3 | Only an admin points a claim at another machine: a change of `spec.assetRef` or `spec.systemRef`. | UPDATE | only an admin may point a claim at another machine |

- A value that did not change passes. So the finalizers of the operator and edits to other fields need no admin.
- Each refusal says who you are, your groups, and where group membership comes from.

<Callout type="caution">
Cluster admin (`system:masters`) is not enough. The policy asks for the group `pk-metal:admins` by name.
A ClusterRoleBinding does not make you a member of a group. Your credential does. See [Get into the admin group](ref:rbac#get-into-the-admin-group).
</Callout>

## `etcdbackuppolicy-guard`

A snapshot holds each Secret of the cluster. The age recipients decide who can decrypt it. The sink decides where the ciphertext goes. A person who adds a recipient can read each later snapshot. So these changes are an admin decision.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin creates a backup policy, or changes `spec.encryption` or `spec.sink`. | CREATE, UPDATE | only an admin may create a backup policy or change its encryption or sink |

- The sink includes the S3 endpoint, the bucket, `credentialsSecretRef` and `caSecretRef`.
- `spec.interval`, `spec.retention` and `spec.suspend` need no admin.
- The CRD schema refuses an `http://` S3 endpoint unless [`allowPlainHTTP`](kind:EtcdBackupPolicy#spec.sink.s3.allowPlainHTTP) is `true`. Set it only for a store in a lab.

## `endpointprofile-guard`

An [](kind:EndpointProfile) has no approval of its own. The operator applies it to each BMC that it selects. It makes an Administrator account, sets the NTP servers, and replaces the TLS identity, which restarts the BMC.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin creates a profile or changes its `spec`. | CREATE, UPDATE | only an admin may create or change an EndpointProfile |

Labels and annotations of a profile need no admin.

## `taloscluster-credentials-guard`

`spec.credentials.ttl` of a [](kind:TalosCluster) sets how long the published admin kubeconfig and talosconfig are valid. Nobody can revoke a copy before it expires. The CRD allows 720 hours at most.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | Only an admin sets `spec.credentials.ttl` to more than 24 hours. | CREATE, UPDATE, when the value changes | only an admin may set spec.credentials.ttl above 24h |

Each person who can patch a cluster can make the time shorter, or remove it. The on-call role can patch clusters.

## `guard-lift`

These annotations lift a safety rule of the operator, or decide a step of a change: `metal.platform-kit.org/override-cluster-guard`, `metal.platform-kit.org/ignore-window`, `metal.platform-kit.org/ack-etcd-risk`, `metal.platform-kit.org/allow-self-disruption`, `metal.platform-kit.org/wipe-waived`, `metal.platform-kit.org/abort` and `metal.platform-kit.org/etcd-snapshot-uploaded`. RBAC lets each holder of `patch` set them. This policy makes the value name that holder. See [Named guard lifts](ref:audit-trail#named-guard-lifts).

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | A request that sets a lift, or changes its value, gives the value `<username>: <reason>`. The username is the username of the request. The reason is not empty. | CREATE, UPDATE | `a guard lift must name you and say why: set … to "<username>: <reason>"` |
| 2 | A request that removes `metal.platform-kit.org/disk-not-wiped` from a Host also sets `metal.platform-kit.org/wipe-waived` to `<username>: <reason>`. The operator is exempt: it removes the mark after a wipe. | UPDATE | `the machine may still hold the install of another cluster: wipe it (pk-metal wipe), or waive the wipe in the same request` |

- A request that removes a lift passes. That puts the rule back.
- A request that leaves the value as it is passes. So the writes of the operator and a value from before the policy pass.
- The operator sets none of these annotations, so it has no exemption from rule 1.
- The policy takes the ConfigMap `hostoperation-approval` as parameters, to know the operator. Without the ConfigMap, it refuses each create and update of the four kinds.
- A GitOps controller that applies a lift names its own identity, or [`guard-lift-stamp`](#guard-lift-stamp) names it. The commit names the person.
- See [](ref:audit-trail) for the records that show the lift.

## `requested-by`

The operator proposes most changes itself, as the result of an edit. The proposal names the operator as proposer. If the site forbids self-approval, this policy makes each such edit name the user who made it, in the annotation `metal.platform-kit.org/requested-by`. The operator copies the names into `spec.requestedBy` of the proposal. Rule 8 of `hostoperation-approval` then applies.

The policy `requested-by-patches` has the same rules for the ConfigMaps with the label `os.platform-kit.org/patch`. It is a separate policy because it selects these ConfigMaps by their label before the API server reads the parameters. So without the parameters, a request on another ConfigMap passes.

The key `selfApproval` of the parameters sets the mode. A missing key is `Allowed`. A value other than `Allowed` is the same as `Forbidden`.

| Mode | An edit without the annotation | An edit of an object with the annotation |
| --- | --- | --- |
| `Forbidden` | Refused if it asks for work | Must name the user of the request if it asks for work |
| `Allowed` | Passes | Must name the user of the request if it asks for work |

An edit asks for work in these cases:

| Kind | Requests that ask for work |
| --- | --- |
| TalosCluster, TalosNode, BiosProfile, FirmwareProfile | Create, a change of `spec`, delete |
| HostClaim | Create, a change of `spec` or of `metal.platform-kit.org/reinstall`, delete (a release) |
| Host | A request that sets or changes `metal.platform-kit.org/wipe` |
| TalosRollout | A change of `spec.abort` or `spec.paused`, or a request that sets `os.platform-kit.org/resume` |
| ConfigMap with the label `os.platform-kit.org/patch` | Create, a change of `data` or `binaryData`, the label set on a ConfigMap without it, delete |

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | A request that asks for work sets `metal.platform-kit.org/requested-by` to the username of the request. If `selfApproval` is `Allowed`, a request on an object without the annotation passes. | CREATE, UPDATE | `this site forbids approving your own change (…), so it must name who asked for it`, or `metal.platform-kit.org/requested-by names "…", who did not make it` |
| 2 | A delete that asks for work needs the annotation to name the user of the delete already. If `selfApproval` is `Allowed`, an object without the annotation passes. Controllers in `kube-system` (the garbage collector, the namespace controller) are exempt. | DELETE | `so it must name who asked for it: first set the annotation`, or `metal.platform-kit.org/requested-by names "…", not you` |
| 3 | A request that changes the annotation sets it to the username of the request. Nobody removes it. This rule applies in the two modes. | UPDATE | `you may set it only to your own username` |

- Rules 1 and 2 apply under `Allowed` to an object with the annotation. Thus the annotation never names a person as the requester of the change of another person.
- Rule 3 applies under `Allowed` too. The operator proposes some time after the edit. The annotation is the record of who asked for a change that is not proposed yet. The next user of a change can replace the name with their own name, so a removal is never necessary.
- If the ConfigMap `hostoperation-approval` is missing, the two policies refuse each request that they check, also a delete by the namespace controller. Restore the ConfigMap.
- Where the site installs [`requested-by-stamp`](#requested-by-stamp), the API server sets the annotation for each create and update that asks for work. Then rule 1 refuses no such request. The operator copies the annotation into `spec.requestedBy`, so the audit trail names the requester. See [](howto:approval-permissions#who-asked-for-a-change).
- The operator has no exemption. It changes no spec of these kinds.
- [](cli:pivot) writes each object as the user that the annotation names. An object without the annotation gets `pk-metal-pivot`.
- The annotation of an object that a GitOps controller applies names the service account of that controller. See [](concept:gitops).

## The name stamps

The kustomize component `config/name-stamp` has three MutatingAdmissionPolicies. They write your username into the annotations that the policies `requested-by`, `requested-by-patches`, and `guard-lift` check. So you do not type your username: not with `kubectl`, not in the manifests of a GitOps controller. The API server applies them before the validating policies, which still check each name.

- They need Kubernetes 1.36 or later, so the base `config/default` does not include them. The sample site overlay and the lab add the component.
- They have no parameters and apply in the two modes of `selfApproval`.
- `failurePolicy: Ignore`. A stamp only saves typing. If it does not apply, the validating policy refuses a request that names nobody. The settings controller does not count a stamp as a gate policy.
- Some seconds after a CRD install, the API server can refuse a write of the new kind with `Resource kind … not found`. Try again after some seconds.
- [](cli:pivot) moves them to the target cluster with the other policies.

### `requested-by-stamp`

For each create and update that asks for work, as the tables of [`requested-by`](#requested-by) say, the API server sets `metal.platform-kit.org/requested-by` to the username of the request. `requested-by-stamp-patches` does the same for the Talos config patches.

- A request that asks for no work stays as it is. A person can still set the annotation to their own name, to take on a change. Nobody can remove it (rule 3).
- A request that writes another name gets the name of its user.
- A delete is not stamped. The API server cannot change an object that goes. A delete that asks for work needs the annotation first (rule 2).

### `guard-lift-stamp`

For each create and update that sets a lift of [`guard-lift`](#guard-lift) to a reason, the API server writes `<username>: ` in front of the reason. For example, `metal.platform-kit.org/ignore-window="CVE fix"` from `alice` becomes `alice: CVE fix`.

- A value that starts with the username of the request stays as it is. The pk-metal commands write that form.
- A value that starts with another name gets the name of the request in front. Nobody writes a lift in the name of another person.
- An empty value and a removal stay as they are. Rule 1 of `guard-lift` refuses the empty value.

## `settings-guard`

The ConfigMap `pk-metal/hostoperation-approval` names the operator and the admin group. It also tells if a person can approve their own change, and how long finished records stay. RBAC lets each holder of `update` on ConfigMaps in `pk-metal` change it. This policy limits that to the admin group.

| # | Rule | When | Message |
| --- | --- | --- | --- |
| 1 | A change of `data`, or a delete, comes from a member of the admin group that the ConfigMap names before the request. A request that does not change `data` passes. | UPDATE, DELETE | `only a member of the admin group "…" may change or delete them` |
| 2 | The key `operator` names a service account (`system:serviceaccount:…`). | CREATE, UPDATE | `the operator key must name the manager's service account` |

- A create is not limited. Without the ConfigMap, each policy that reads it refuses each request, so the create is the install.
- The namespace controller in `kube-system` can delete the ConfigMap with its namespace.
- The operator writes a `settings.changed` line for each change that it sees. See [](ref:audit-trail).

## The check of the gate

The operator checks each policy of this page one time each minute. It reports a policy that is missing, has a `failurePolicy` other than `Fail`, or has no binding that denies. A binding of a policy with parameters must also have `parameterNotFoundAction: Deny`. The operator then sets the metric `pk_metal_admission_gate_degraded` to 1 for the policy, and writes a `gate.degraded` line. The alert `PkMetalAdmissionGateDegraded` links [](rb:admission-gate-degraded). The operator changes no policy.
